1. Em 30 segundos

O MediAgenda é um sistema de marcação e gestão de consultas médicas de uma clínica com presença nas principais cidades de Moçambique. É um monólito modular:

Camada Tecnologia Pasta
Interface React 18 + Vite (JavaScript, CSS próprio) web/src
API Node.js 24 + Express server/src/api
Domínio / padrões State, Chain, Strategy, Factory, Adapter, Command, Façade, Observer server/src/domain, commands, services, events
Persistência SQLite nativo (node:sqlite), sem ORM server/src/repositories, db
Testes node:test (52 testes) server/tests

O que distingue o trabalho:

  1. Os padrões estão a correr, não apenas desenhados. A cadeia de validação é executada a cada marcação e o resultado (com tempos por elo) fica gravado e visível no X-Ray.
  2. Aprovação real de contas: médico só entra depois de a secretária confirmar; secretária só entra depois de o administrador autorizar.
  3. Confirmação por e-mail com link de uso único (SMTP real via nodemailer, com fallback para outbox quando não há servidor configurado).
  4. Permissões operacionais separadas: o administrador vê e configura, mas não confirma, cancela nem reagenda consultas.
  5. Rede nacional: 16 médicos activos em 8 cidades (Maputo, Matola, Beira, Nampula, Quelimane, Tete, Chimoio, Pemba) + 2 contas pendentes para demonstrar as aprovações.

5. Onde está cada padrão (com o código)

5.1 Singleton — server/src/config/ConfiguracaoSistema.js

export class ConfiguracaoSistema {
  static #instancia = null;
  static obterInstancia() {
    if (!ConfiguracaoSistema.#instancia) {
      ConfiguracaoSistema.#instancia = new ConfiguracaoSistema();
    }
    return ConfiguracaoSistema.#instancia;
  }

Uma única configuração (horário, antecedência, limites, prazo de confirmação) partilhada por todos os serviços. Alterações em Admin → Configuração entram imediatamente na cadeia de validação.

5.2 Chain of Responsibility — server/src/domain/validacao/cadeia.js

export class Validador {
  definirProximo(validador) { this.proximo = validador; return validador; }
  executar(contexto) {
    const resultado = this.verificar(contexto);
    if (!resultado.ok) return { ok: false, falhouEm: this.codigo };
    return this.proximo ? this.proximo.executar(contexto) : { ok: true };
  }
}

Cinco elos independentes, por esta ordem:

Ordem Classe Regra
1 AntecedenciaMinima RN-01
2 HorarioFuncionamento RN-09 (horário + disponibilidade + bloqueios)
3 ConflitoAgenda RN-05
4 LimiteDiarioMedico RN-03
5 LimitePaciente RN-06

Onde ver na UI: ao marcar, o modal mostra os 5 elos com ✅/❌ e a duração de cada um. O trace fica em validacoes_traces e aparece no X-Ray da consulta e no Architecture Lab.

5.3 State — server/src/domain/consulta/estados.js

export class EstadoPendente extends EstadoConsulta {
  confirmar(consulta, agora) { /* RN-07: só dentro do prazo */ }
  cancelar(consulta, agora) { /* RN-02: calcula se é tardio */ }
  get transicoes() { return ['confirmada', 'cancelada']; }
}

pendente ──confirmar──► confirmada ──realizar──► realizada
   │                        │
   └──────cancelar──────────┴──► cancelada

Cada estado recusa operações inválidas com TRANSICAO_INVALIDA (HTTP 409) — não há if (estado === 'pendente') espalhado pelos serviços.

5.4 Strategy — server/src/domain/notificacao/estrategias.js

const ESTRATEGIAS = {
  email: new EstrategiaEmail(),
  sms: new EstrategiaSMS(),
  ambos: new EstrategiaAmbos(),
  whatsapp: new EstrategiaWhatsApp()
};
export function obterEstrategiaNotificacao(preferencia) {
  return ESTRATEGIAS[preferencia] || ESTRATEGIAS.email;
}

Duas estratégias: canal de notificação (preferência do utilizador) e duração da consulta (DuracaoPadrao vs. DuracaoPorEspecialidade, RN-04, limitada a 60–120 min). Demonstração: Perfil → Notificações → WhatsApp; sem telefone recua para e-mail.

5.5 Factory Method — server/src/domain/notificacao/factory.js

export class NotificacaoFactory {
  criar(tipo) {
    if (tipo === 'email') return new EmailNotificacao(this.#email);
    if (tipo === 'sms') return new SMSNotificacao(this.#sms);
    if (tipo === 'whatsapp') return new WhatsAppNotificacao(this.#whatsapp);
    throw new Error(`Tipo de notificação desconhecido: ${tipo}`);
  }
}

Quem chama pede criar('email') e recebe a classe concreta — sem conhecer a construção. Acrescentar um canal novo não altera o NotificacaoService.

5.6 Adapter + ISP — server/src/domain/notificacao/canais.js

export class IEnviadorEmail {
  async enviarEmail() { throw new Error('não implementado'); }
}

export class AdapterSMTP extends IEnviadorEmail {
  get configurado() { return Boolean(this.host && this.utilizador && this.password); }

  async enviarEmail({ para, assunto, corpo }) {
    // grava sempre uma cópia em outbox/email
    if (!this.configurado) return { id, ficheiro, provedor: 'SMTP simulado (outbox)' };
    const transporte = await this.#obterTransporte();      // nodemailer
    const info = await transporte.sendMail({ from: this.remetente, to: para, subject: assunto, text: corpo });
    return { id, ficheiro, provedor: 'SMTP real (nodemailer)', messageId: info.messageId };
  }
}
  • IEnviadorEmail, IEnviadorSMS e IEnviadorWhatsApp são interfaces pequenas (ISP).
  • O AdapterWhatsApp foi acrescentado sem alterar nenhum serviço existente.
  • O AdapterSMTP fala SMTP real (nodemailer) quando existem variáveis de ambiente; sem elas grava em server/outbox/email para a demonstração offline.

5.9 Observer + EDA + Outbox — server/src/events/EventBus.js

async publicar(tipo, payload) {
  const eventoId = this.#eventoRepository.criar(tipo, payload);   // outbox primeiro
  for (const { nome, handler } of this.#subscritores.get(tipo) || []) {
    await handler({ id: eventoId, tipo, payload });
    this.#eventoRepository.registarConsumo(eventoId, nome, 'sucesso', null);
  }
  this.#eventoRepository.marcarProcessado(eventoId);
}

RelatorioService invalida a cache dos KPIs
AuditoriaService regista EVENTO:<tipo>

Onde ver na UI: Architecture Lab → Event Monitor (eventos, consumidores e outbox) e a página Notificações.

6.1 Regras novas pedidas para a defesa

Regra Onde está implementada Onde se vê na UI
Médico só entra após confirmação da secretária AuthService.registar (estadoAprovacao='pendente', ativo=0), AuthService.login (APROVACAO_PENDENTE), AuthService.aprovar /registo (aviso), /secretaria → Médicos & aprovações
Secretária só funciona após autorização do administrador AuthService.#garantirPoderDeAprovacao, admin.js /admin → Aprovações
Secretária também pode criar médicos POST /api/secretaria/medicos /secretaria → + Novo médico

Administrador não faz operações operacionais verificação de perfil nas Commands e no ConsultaService no admin os botões desaparecem; API devolve 403

6.2 Fluxo de aprovação

Formulário público /registo
        │
        ├── paciente   → conta activa de imediato
        │
        ├── médico     → estado_aprovacao = 'pendente', ativo = 0
        │                 └── notifica secretária + admin
        │                 └── secretária aprova → login passa a funcionar
        │
        └── secretária → estado_aprovacao = 'pendente', ativo = 0
                          └── notifica admin
                          └── admin aprova → login passa a funcionar

Em users ficam estado_aprovacao, aprovado_em, aprovado_por. Enquanto pendente, o login devolve 403 APROVACAO_PENDENTE (a palavra-passe é validada primeiro, para não revelar se o e-mail existe).

A secretária não aprova secretárias: a regra está no servidor (AuthService.#garantirPoderDeAprovacao) e devolve 403 mesmo por chamada directa à API.

6.3 Confirmação de consulta por link (uso único)

  1. Ao marcar, a Façade gera token_confirmacao e guarda-o na consulta.
  2. O e-mail inclui http://localhost:5173/confirmar-consulta?id=<id>&token=<token>.
  3. A página pública mostra médico, especialidade, data e paciente.
  4. Ao confirmar, ConsultaService.confirmarPorLink valida o token, aplica o State (RN-07) e apaga o token — o link deixa de funcionar (404).
  5. Link pronto no seed: http://localhost:5173/confirmar-consulta?id=6&token=demo-consulta-pendente

6.4 Confirmação de e-mail (registo)

POST /api/auth/registo gera token_confirmacao e envia o link http://localhost:5173/confirmar-email?token=.... A página confirma sem sessão e regista auditoria (EMAIL_CONFIRMADO). O formulário mostra o link em modo demonstração, para não depender de uma caixa de correio real durante a apresentação.

  • Gmail exige palavra-passe de aplicação (conta com verificação em dois passos).
  • Mailtrap (sandbox): SMTP_HOST=sandbox.smtp.mailtrap.io, porta 2525.
  • Se o envio real falhar, a notificação fica registada com erro e a cópia em outbox continua disponível — a demonstração nunca fica bloqueada.
  • Prova rápida: Registo de um paciente → abrir server/outbox/email (ou a caixa real) → clicar no link confirmar-email.

9. Perguntas prováveis do docente

“Porque SQLite e não MySQL?” Zero configuração para a defesa e para o deploy num único processo; o acesso está isolado em repositórios, pelo que a migração para PostgreSQL muda apenas essa camada.

“Onde está a regra X?” Todas as RN-01…RN-09 estão na tabela da secção 6, com a classe e o ficheiro. As validações de marcação estão em domain/validacao/cadeia.js; as transições em domain/consulta/estados.js.

“A aprovação está só na interface?” Não. AuthService.login valida estado_aprovacao e devolve 403. Mesmo chamando a API directamente, um médico pendente não entra. A secretária também não aprova secretárias — o servidor recusa.

“Como garantem que o administrador não cancela consultas?” As Commands (CancelarConsultaCommand, ReagendarConsultaCommand) e o ConsultaService.realizar verificam o perfil e lançam ErroProibido. Os botões desaparecem na UI, mas a defesa está no servidor.

“A RN-08 não é uma operação do administrador?” A desactivação é pedida pelo admin, mas o cancelamento das consultas futuras é executado por um utilizador interno { perfil: 'sistema' } — o admin não exerce uma operação operacional.

“O e-mail é real?” Com SMTP_* definido, sim: o AdapterSMTP usa nodemailer e envia pela rede. Sem configuração, grava em server/outbox/email para a demonstração continuar offline. Em ambos os casos fica cópia em outbox para auditoria.

“O que acontece se o processo cair a meio de um evento?” O evento é gravado primeiro na tabela eventos (outbox) e só depois distribuído; cada consumo fica em evento_consumos. É a base para reprocessamento idempotente.

“Quantos testes têm?” 52, com node:test, em bases temporárias: estados, regras, aprovações, permissões, EDA, segurança, API e canais.

“Onde está a prova de que os padrões funcionam juntos?” No fluxo de marcação: Façade → Strategy (duração) → Chain (RN) → Repository (persistência) → EventBus (Observer) → Factory/Adapter (notificação) → Auditoria, com State a controlar transições.
